# Releasing

How to produce a downloadable build, what each output is for, and what is still
required before a build should be called stable.

Everything below was run end to end on Windows 11: the PyInstaller build, the
Inno Setup compile, a silent install, a launch of the installed application, and
a silent uninstall.

## What you can publish today

**Without a code-signing certificate**, `-SkipSigning` produces two real,
installable artifacts:

```powershell
.\scripts\build_release.ps1 -Version 0.8.0 -Channel stable -SkipSigning
```

| Output | Use |
| --- | --- |
| `dist\installer\DuplicateTransferManagerSetup-<version>.exe` | Per-user installer, ~37 MB. Start menu entry, optional desktop shortcut, Add/Remove Programs entry, uninstaller. |
| `dist\installer\DuplicateTransferManager-<version>-portable.zip` | Unzip and run. No installation, no elevation, and no SmartScreen installer prompt. |
| `dist\installer\update-manifest-<version>.json` | Only meaningful once signed; see below. |

**Expect a SmartScreen warning on an unsigned installer.** Windows shows
"Windows protected your PC" and the user must click *More info → Run anyway*.
This is normal for a new, unsigned publisher and is the single strongest reason
to buy a certificate. The portable ZIP avoids the installer prompt, though
Windows still marks files downloaded from the internet.

Do not advertise an unsigned build as a stable release. Label it a preview and
say plainly that it is unsigned, so the warning does not look like a compromise.

## Prerequisites

| Tool | Needed for | Install |
| --- | --- | --- |
| Python 3.12 | everything | `winget install --id Python.Python.3.12 -e` |
| PyInstaller | the executable | `pip install -r requirements-dev.txt` |
| Inno Setup 6 | the installer | `winget install --id JRSoftware.InnoSetup -e` |
| Windows SDK `signtool` | signing only | Windows SDK, or already present with Visual Studio |

winget installs Inno Setup per-user, under
`%LOCALAPPDATA%\Programs\Inno Setup 6`, not into Program Files. The build script
checks both locations and `PATH`.

## Producing a signed release

Two independent pieces of key material are required, and neither can be
generated by the build:

1. **An Authenticode code-signing certificate**, bought from a CA. Set
   `WINDOWS_SIGNING_CERT_THUMBPRINT` to its thumbprint. An OV certificate is
   cheaper; an EV certificate clears SmartScreen immediately but requires a
   hardware token.
2. **An update-manifest signing key**, which is yours to generate. The committed
   `packaging/update_public_key.json` is a **1024-bit development key** and must
   be replaced before any public release. See [SECURITY.md](../SECURITY.md).

```powershell
$env:WINDOWS_SIGNING_CERT_THUMBPRINT = "<thumbprint>"
.\scripts\build_release.ps1 -Version 0.9.0 -Channel stable `
    -ManifestPrivateKey C:\keys\update-manifest-private.pem `
    -MinimumSupportedVersion 0.8.0
```

The script runs the full test suite first and stops on failure.

`-MinimumSupportedVersion` is the oldest installed version allowed to take this
update. Raise it when an upgrade cannot be applied safely from older builds.

## What the build actually does

1. Installs dev dependencies and runs the test suite.
2. Generates the application icon.
3. Builds the executable with PyInstaller, stamping a Windows version resource
   read from `src/duplicate_transfer_manager/version.py`.
4. Signs the executable, unless `-SkipSigning`.
5. Downloads the Android Platform Tools, checks the release is at least
   `minimum_version` from `packaging/android_platform_tools_manifest.json`,
   copies `platform-tools` next to the executable, and records the version it
   actually got in `platform-tools/bundled_version.txt`. The application prefers
   this copy over anything on `PATH`, and diagnostics report the recorded
   version.

   Google publishes only the latest platform-tools at a stable URL — the
   versioned archives stop before 36 — so an exact-version assertion is not
   possible and previously failed the build on every Google release. The check
   is a floor, not a pin.
6. Compiles the Inno Setup installer, signing it and the uninstaller unless
   `-SkipSigning`.
7. Writes the portable ZIP.
8. Writes the update manifest and signs it if a private key was supplied.

## Publishing to GitHub Releases

The workflow in `.github/workflows/release.yml` does the same on a runner and
uploads a draft release. It requires these repository secrets:

- `WINDOWS_SIGNING_CERT_BASE64`, `WINDOWS_SIGNING_CERT_PASSWORD`,
  `WINDOWS_SIGNING_CERT_THUMBPRINT`
- `UPDATE_MANIFEST_PRIVATE_KEY_PEM`

Without them the workflow fails by design; build locally with `-SkipSigning`
for a preview instead.

Attach the SHA-256 values the script prints to the release notes so downloads
can be verified.

## Before calling a build stable

- [ ] Replace the 1024-bit development update key with a production key.
- [ ] Obtain an Authenticode certificate and produce a signed build.
- [ ] Bump `src/duplicate_transfer_manager/version.py`; the installer, the
      executable's version resource, and the manifest all read from it.
- [ ] Update [CHANGELOG.md](../CHANGELOG.md).
- [ ] Walk [TARGETED_FIX_MANUAL_CHECKLIST.md](TARGETED_FIX_MANUAL_CHECKLIST.md)
      on a real machine with a real Android phone. No automated test covers
      device behaviour.
- [ ] Install over a previous version and confirm settings, quarantined files,
      and history survive.
- [ ] Review the open findings in [PROGRAM_AUDIT.md](PROGRAM_AUDIT.md).

## Version numbering

`src/duplicate_transfer_manager/version.py` is the single source of truth. The
executable's version resource, the installer's `AppVersion`, and the update
manifest all derive from it, and a test asserts the spec reads it rather than
hardcoding a value.
